1. Création de la fenêtre SFML

Vue annotée de la scène — chaque flèche relie un élément visuel à sa classe C++

La fenêtre est la première chose créée dans main.cpp. SFML gère pour toi l'ouverture d'une fenêtre native Windows/Linux avec une surface de rendu GPU.

// Window size = 12 colonnes × 64px = 768, 9 lignes × 64px = 576
sf::RenderWindow window(sf::VideoMode(768, 576), "Tower Defense - Visual Test");
window.setFramerateLimit(60);

Que fait chaque ligne ?

CodeRôle
sf::RenderWindowClasse SFML qui encapsule une fenêtre OS + une surface de dessin OpenGL
sf::VideoMode(768, 576)Définit la résolution : largeur × hauteur en pixels
setFramerateLimit(60)Limite à 60 images/sec pour ne pas brûler le CPU. Sans ça la boucle tourne à 10 000 FPS.

La boucle d'événements

sf::Event event;
while (window.pollEvent(event))
{
    if (event.type == sf::Event::Closed)
        window.close();       // Croix rouge → ferme la fenêtre
    if (event.type == sf::Event::KeyPressed
        && event.key.code == sf::Keyboard::Escape)
        window.close();       // Echap → ferme aussi
}

Pourquoi une boucle d'événements séparée ?

SFML accumule les événements dans une file d'attente interne. pollEvent() les dépile un par un. Sans cette boucle la fenêtre se fige (elle n'enregistre plus les clics ni la fermeture).

2. La Map — Système de Tilemap

📸 Capture 1 : la map avec le chemin en S

La map est une grille 2D de 12 colonnes × 9 lignes. Chaque cellule contient un entier qui indique le type de tuile à afficher.

Le rendu de la grille (Map::draw)

void Map::draw(sf::RenderWindow& window) {
    sf::Sprite sprite;
    for (int row = 0; row < MAP_ROWS; ++row) {
        for (int col = 0; col < MAP_COLS; ++col) {

            // Choisir la texture selon la valeur dans GRID
            switch (GRID[row][col]) {
                case 1:  sprite.setTexture(m_texPath);  break;
                default: sprite.setTexture(m_texGrass); break;
            }

            // Redimensionner la tuile à 64×64 pixels
            auto sz = sprite.getTexture()->getSize();
            sprite.setScale(TILE_SIZE / (float)sz.x,
                            TILE_SIZE / (float)sz.y);

            // Positionner la tuile dans la fenêtre
            sprite.setPosition(col * TILE_SIZE, row * TILE_SIZE);
            window.draw(sprite);
        }
    }
}

Conversion grille → pixels

La cellule à la colonne col et ligne row s'affiche au pixel (col × 64, row × 64). Avec TILE_SIZE = 64, la grille 12×9 occupe exactement 768×576 pixels — soit toute la fenêtre.

3. Sprites et Textures SFML

SFML sépare l'image (texture) de l'objet dessinable (sprite). C'est une distinction importante.

ClasseRôleVit dans
sf::TextureStocke les pixels de l'image en mémoire GPUMembre privé de la classe (ex: m_texture)
sf::SpriteObjet dessinable : position, rotation, scale, lien vers une TextureHérité de Entity via m_sprite

⚠️ Piège classique : la Texture doit survivre au Sprite

Un sf::Sprite garde un pointeur brut vers sa Texture. Si la Texture est détruite avant le Sprite (variable locale, pointeur libéré), le Sprite dessine de la mémoire invalide → crash ou artefacts visuels. C'est pourquoi m_texture est un membre de la classe, pas une variable locale.

Chargement d'une texture et liaison au sprite

// Tower::loadTexture — charge depuis disk et prépare le sprite
bool Tower::loadTexture(const std::string& path) {
    if (!m_texture.loadFromFile(path)) {
        std::cerr << "Failed to load: " << path << "\n";
        return false;
    }
    m_sprite.setTexture(m_texture);         // Lie la texture au sprite

    auto sz = m_texture.getSize();           // Taille originale de l'image (ex: 64×64)
    m_sprite.setScale(48.f / sz.x,
                       48.f / sz.y);        // Réduit à 48×48 dans la tuile
    m_sprite.setPosition(m_position.x + 8.f,
                           m_position.y + 8.f); // Centre dans la tuile 64×64
    return true;
}

Calcul du scale

Image originale : 64 × 64 px Taille cible : 48 × 48 px scaleX = 48.0 / 64.0 = 0.75 scaleY = 48.0 / 64.0 = 0.75 Marge dans la tuile : (64 - 48) / 2 = 8 px de chaque côté → setPosition(tileX + 8, tileY + 8)

4. Héritage et Polymorphisme

Toutes les entités du jeu (tours, ennemis) partagent une classe de base : Entity. Cela permet de les traiter de façon uniforme.

// entity.hpp — classe de base abstraite
class Entity {
protected:                        // Accessible aux sous-classes
    int          m_hpMax;
    int          m_hpCurrent;
    sf::Sprite   m_sprite;        // Partagé par tous les enfants
    sf::Vector2f m_position;

public:
    bool         takeDamage(int damage);
    virtual void update(float deltaTime) = 0; // Méthode pure → classe abstraite
    virtual void render(sf::RenderWindow&) const = 0;
    virtual ~Entity() = default;  // Destructeur virtuel obligatoire
};

Arbre d'héritage

Entity (abstraite) / \ Enemy Tower / \ / | \ GOBLIN BOSS ARCHER MAGE CANNON

Pourquoi virtual ?

// Sans virtual : Entity::render() est appelé → rien ne s'affiche
// Avec virtual  : Enemy::render() ou Tower::render() est appelé → correct

std::shared_ptr<Entity> e = make_shared<Enemy>(...);
e->render(window); // Appelle Enemy::render() grâce au vtable

Destructeur virtuel

virtual ~Entity() = default est obligatoire quand on détruit un objet dérivé via un pointeur de base. Sans ça, seul le destructeur de Entity est appelé → fuite mémoire / comportement indéfini.

5. Smart Pointers — std::shared_ptr

Dans ce projet on utilise std::shared_ptr pour gérer la durée de vie des ennemis et des tours. Pas de new / delete manuels.

Création

// make_shared alloue l'objet ET le compteur de référence en un seul bloc mémoire
std::shared_ptr<Enemy> goblin = std::make_shared<Enemy>(EnemyType::GOBLIN, waypoints);

Stockage dans un vecteur

std::vector<std::shared_ptr<Enemy>> enemies = { goblin, boss };

// Itération avec référence pour éviter une copie du shared_ptr
for (auto& enemy : enemies)
    enemy->update(dt);
ConceptExplication
Compteur de référenceChaque shared_ptr incrémente un compteur. Quand il tombe à 0, l'objet est détruit automatiquement.
make_sharedPréférable à new : une seule allocation mémoire, exception-safe.
auto& dans la boucleRéférence au shared_ptr : pas de copie, le compteur ne monte pas inutilement.
operator->Accède aux membres de l'objet pointé, comme un pointeur brut.

shared_ptr vs raw pointer

Raw pointer : Enemy* e = new Enemy(...); // → doit appeler delete e; manuellement // → si oublié = fuite mémoire // → si double delete = crash shared_ptr : auto e = make_shared<Enemy>(...); // → détruit automatiquement quand plus personne ne l'utilise // → safe même si exception levée

Pourquoi pas unique_ptr ici ?

unique_ptr signifie un seul propriétaire. Ici la Tour et le WaveController ont tous les deux besoin d'accéder aux ennemis → il faut shared_ptr pour la propriété partagée.

6. Les Waypoints — Chemin des ennemis

Le chemin en S — 6 waypoints en pixels. L'ennemi avance de ① vers ⑥ via m_pathIndex.

Les ennemis ne connaissent pas la grille. Ils suivent une liste de points GPS en pixels : les waypoints. La Map les calcule une seule fois au chargement.

// Map.cpp — calcul des waypoints en pixels à partir de la grille
float half = TILE_SIZE / 2.f;  // = 32px → centre d'une tuile

m_waypoints = {
    {0.f,                  2 * TILE_SIZE + half},  // Entrée gauche,  pixel (0,   160)
    {4 * TILE_SIZE + half, 2 * TILE_SIZE + half},  // Virage bas,     pixel (288, 160)
    {4 * TILE_SIZE + half, 4 * TILE_SIZE + half},  // Virage droite,  pixel (288, 288)
    {7 * TILE_SIZE + half, 4 * TILE_SIZE + half},  // Virage bas,     pixel (480, 288)
    {7 * TILE_SIZE + half, 6 * TILE_SIZE + half},  // Virage droite,  pixel (480, 416)
    {12.f * TILE_SIZE,     6 * TILE_SIZE + half},  // Sortie droite,  pixel (768, 416)
};

Passage des waypoints à l'ennemi

// main.cpp — les waypoints de la map sont passés par référence constante
const std::vector<sf::Vector2f>& waypoints = map.getWaypoints();

// Le vecteur est copié dans chaque ennemi (chaque ennemi a sa propre position)
auto goblin = make_shared<Enemy>(EnemyType::GOBLIN, waypoints);

const std::vector<sf::Vector2f>& — pourquoi cette signature ?

const : on ne modifie pas les waypoints.
& : on ne copie pas le vecteur (potentiellement des centaines d'éléments).
Le vecteur est ensuite copié dans le constructeur Enemy pour que chaque ennemi ait son propre index de progression.

7. Le Mouvement des Ennemis

Décomposition mathématique du mouvement — de la position actuelle au waypoint suivant

Chaque frame, l'ennemi calcule la direction vers le prochain waypoint et avance d'une distance proportionnelle au temps écoulé (deltaTime).

void Enemy::update(float deltaTime) {
    if (m_pathIndex >= (int)m_path.size()) return; // Sorti de la map

    sf::Vector2f target    = m_path[m_pathIndex];  // Prochain waypoint
    sf::Vector2f direction = target - m_position;   // Vecteur vers la cible
    float distance = std::sqrt(direction.x * direction.x
                              + direction.y * direction.y);

    if (distance < 2.f) {
        m_pathIndex++;                             // Waypoint atteint → suivant
    } else {
        sf::Vector2f normalized = direction / distance; // Longueur = 1
        m_position += normalized * m_speed * deltaTime;
        m_sprite.setPosition(m_position);
    }
}

Explication mathématique du mouvement

Positions : m_position = (200, 160) ← position actuelle target = (288, 160) ← prochain waypoint Vecteur direction : direction = (288-200, 160-160) = (88, 0) Distance (norme du vecteur) : distance = sqrt(88² + 0²) = 88 Vecteur normalisé (longueur = 1) : normalized = (88/88, 0/88) = (1.0, 0.0) ← pur mouvement horizontal Déplacement cette frame (à 60 FPS, dt ≈ 0.0166s, speed = 100) : déplacement = (1.0, 0.0) × 100 × 0.0166 = (1.66, 0) pixels/frame Nouvelle position : m_position = (200 + 1.66, 160) = (201.66, 160)

Pourquoi normaliser le vecteur ?

Sans normalisation, un ennemi qui est loin de sa cible irait plus vite qu'un ennemi proche. En divisant par la distance, on obtient toujours un vecteur de longueur 1, et la vitesse devient exclusivement contrôlée par m_speed.

Le problème actuel : pas de rotation du sprite

L'ennemi avance dans la bonne direction en coordonnées, mais son sprite reste toujours orienté dans la même direction. Pour corriger, il faut calculer l'angle de la direction et appeler m_sprite.setRotation(angle).

// Fix à appliquer dans update() :
float angle = std::atan2(direction.y, direction.x) * 180.f / M_PI;
m_sprite.setRotation(angle);

8. Références vs Pointeurs

Ce projet utilise les deux. Voici où et pourquoi.

Références (&)

// Référence constante : lecture seule, pas de copie
const std::vector<sf::Vector2f>& getWaypoints() const;

// Référence modifiable : on modifie la vraie fenêtre, pas une copie
void draw(sf::RenderWindow& window);

// Référence dans la boucle for : pas de copie du shared_ptr
for (auto& enemy : enemies) { ... }

Pointeurs intelligents (shared_ptr)

// Pointeur partagé : plusieurs propriétaires possibles
std::shared_ptr<Enemy> goblin = make_shared<Enemy>(...);

// Accès à l'objet via ->
goblin->update(dt);

// Passage à une fonction : copie du shared_ptr (compteur +1)
void attack(std::vector<std::shared_ptr<Enemy>>& enemies);

9. La Boucle de Jeu — Game Loop

La boucle tourne 60 fois par seconde. Chaque itération = 1 frame.

→
Display

↺

Le deltaTime

sf::Clock clock;

while (window.isOpen()) {
    float dt = clock.restart().asSeconds(); // Temps depuis la dernière frame

    // dt ≈ 0.0166s à 60 FPS, ≈ 0.033s à 30 FPS
    // En multipliant par dt, la vitesse est la même quelle que soit la FPS
    enemy->update(dt);
}

Pourquoi deltaTime est essentiel

Sans deltaTime, un ennemi à speed=100 avancerait de 100px par frame. À 60 FPS = 6000px/sec. À 30 FPS = 3000px/sec. Avec deltaTime, il avance de 100 × dt pixels, soit toujours 100px/seconde, peu importe le framerate.
